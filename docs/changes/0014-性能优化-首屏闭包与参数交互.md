- 状态：已执行
- 影响范围：`src/lib/{render,export,exportImage,importData}.ts`、`src/export/{run,runImage}.ts`、`src/components/{PressSheet,BatchPreviewGrid}.tsx`、`DESIGN.md`、`package.json`
- 前置文档：[0013-加固-边界输入与失败可见.md](0013-加固-边界输入与失败可见.md)
- 生效版本：**0.5.3**（导出件、毫米读数、默认值、界面语言全部不变；变的只有「什么时候下载哪块代码」与「预览位图按多大分辨率画」）

## 背景（先测，再改）

按 `/impeccable optimize` 的顺序走：量 → 找真瓶颈 → 改 → 复量。两条轴都量了，且都先用**对照**确认不是噪声：

| 轴 | 量法 | 基线（本机 localhost + 生产构建） |
| --- | --- | --- |
| 首屏 | 入口 HTML → BFS 跟随静态 import 的首屏闭包；Chromium 的 paint / resource 计时 | 入口 **1569 kB（gzip 491 kB）**；FCP 540ms；长任务 380ms；入口 chunk 里就有 jsPDF（86 处标记）与 docx |
| 交互 | 页面内 rAF 帧间隔探针 + 真实键盘：对「字号」做 10 步连击（滑杆拖动的等价负载） | A4：maxGap **89ms**、>50ms 帧 **10–20**；**同操作在 60×40 贴纸上 maxGap 11ms、0 帧** |

「A4 卡、贴纸不卡」这条对照把范围锁到「与印张像素量成正比的某一步」，于是逐个证伪：

| 假设 | 证伪方式 | 结果 |
| --- | --- | --- |
| 画布分配（`canvas.width` 赋值） | 埋点计时该属性写入 | 10 次共 **0ms** |
| `drawImage`（大码位图缩进预览） | 埋点计时画布操作 | 每步 1 次、**0.2ms** |
| 每步换一张新 canvas 元素 | 改为常驻复用画布后复测 | 仍 **156ms**（不是它） |
| 上墨动效的 `filter: blur` | 页面里临时禁用该动画后复测 | 仍 **144ms**（不是它） |
| 刻度尺 SVG 每步重建（数量随尺寸增长） | 给 `SheetRuler` 加 `memo` 后复测 | 仍 **122ms**（不是它） |

**真因**：预览位图远大于它在屏幕上的显示尺寸。A4 适应窗口时画布是 1272×1800（`PREVIEW_MAX_PX = 1800` 封顶），而台面上只显示 923×1306 CSS px → 浏览器每帧都要把整张位图**二次缩放并重新栅格化**；贴纸尺寸的画布本来就小于显示框，所以不卡。

首屏侧的真因更直接：`lib/export.ts` 顶部静态 `import { jsPDF } from 'jspdf'` 与 `from 'docx'`、`lib/exportImage.ts` 的 `zipSync`、`lib/importData.ts` 的 `read-excel-file` —— 四份「只在导出/导入时才用」的库被算进了打开页面的代价（合计约 500 kB 原始 / 150 kB gzip）。

**明确不做**：不动导出链路的像素口径（导出必须满 DPI，二维码模块尺寸只在导出网格上决定）；不做虚拟滚动、不加 rAF 合并预览的「少出几帧」策略（会改变上墨手感，属产品决策）；不为了首屏去动 MUI / React。

## 方案

| 项 | 做法 |
| --- | --- |
| 首屏闭包 | 四个重库改**动态导入**：`createPdfBuilder()` 变 async 并在内部 `await import('jspdf')`；`exportWord` 内 `await import('docx')`（模块级 `ALIGNMENT_BY_ALIGN` 常量随之下沉为函数内 `alignOf`）；ZIP 分支内 `await import('fflate')`；`parseXlsxFile` 内 `await import('read-excel-file/browser')`。类型用 `import type` 保留，运行时形状按需取 |
| 预览分辨率 | `PressSheet` 改成按台面**实际显示像素**渲染：`scale = min(PREVIEW_MAX_PX 封顶, pxPerMm × 25.4 × DPR / 导出 dpi)`；`renderLabel` 新增可选 `into?: HTMLCanvasElement`，预览传一张常驻画布（`useState` 惰性初始化），尺寸没变就不重设 width/height |
| 上墨动效 | 画布常驻后不能再靠 `key` 重挂来重放动画（重挂会换掉画布），改为 `signature` 变化时 `style.animation='none'` → 强制重排 → 复位，显式从头放一遍 |
| 刻度尺 | `SheetRuler` 与 `Readout` 用 `memo` 包住：刻度只取决于长度与密度，参数改动不该重建几百个 SVG 元素 |
| 缩略图 | `BatchPreviewGrid` 的出片同样按**格子实际显示像素**（`holder.clientWidth × DPR`，仍受 `THUMB_MAX_PX` 封顶）渲染，并复用该格已有的画布（760px 位图塞进 ~150px 的格子是同一类浪费） |

**已知限制**（诚实记录）：

- 交互仍有残余开销：预览本来就每次重画整张印张，剩下的时间花在「浏览器重新栅格化这块位图」本身；A4 连击仍有 2–5 帧 >50ms。要再降就得改成 rAF 合并（一次拖动只出最后一帧），那会改变上墨手感，留作产品决策。
- 首屏 221 kB（gzip）里主要是 React + MUI + emotion + qrcode；再瘦需要动组件库或改渲染路径，风险大于收益。
- 本机 FCP 444ms 里传输不是大头（localhost）；真实收益体现在 491 → 221 kB 的下载量（内网/弱网更明显）。
- XLSX 路径用自造的最小工作簿验证（真实业务表未测）；`.xls` 仍是明确拒绝。
- 一次性探针（帧间隔脚本、xlsx 生成器）都放在仓库外（`~/.local/tmp/qrstick-perf/`），未入库。

## 后续验证建议

1. 弱网真机复测：`bun run build && bun run preview`，DevTools 限速 3G，确认首屏只拉 entry + CSS，导出时才拉 jspdf / docx / fflate / xlsx。
2. 低端机复测：DPR 1 的老设备上重复「字号/页边距连击」，Performance 面板确认没有持续 >50ms 的长任务。
3. 度量口径固定下来：判「首屏是否回归」只看**首屏闭包**（入口 + 静态 import 链），不看入口 chunk 单文件大小（Rollup 会在入口与共享块之间重新归并）。
4. 若后续新增重库，先问它属于首屏还是某次动作：只有首屏渲染真正需要的才允许静态 import。
